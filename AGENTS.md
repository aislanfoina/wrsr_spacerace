# AGENTS.md - Space Race (context for AI agents)

Read this before changing anything. It is the condensed working knowledge of the sessions that
built this mod: what exists, how it is built and tested, which engine facts it stands on, and the
traps that already cost time. `README.md` is the player-facing page; `docs/space-race-design.md`
is the long design and test history (every address and every in-game test, dated).

---

## 1. What this is

A mod for **Workers & Resources: Soviet Republic 1.1.1.9** (`SOVIET64.exe`, image base
0x140000000; every address below is an RVA valid for this build only). It adds a Soviet space
programme to any ordinary game: a research branch, 16 buildings, 5 rockets, optional new goods, a
fourth education tier (cosmonauts / chief designers), and a scenario ("the programme") that runs
eight milestones against the real American timeline. The last milestone is an N1 Moon landing
before Apollo 11 (20 July 1969).

Runs on **Republic Mod Loader (RML)**, Workshop item 3787969749, which hosts TesmioLoader-API
plugins (API 3/4). Three plugins (all C++, MSVC x64, /MT): `spacerace`, `experts`, `resources`.

Status (2026-10-05): every feature has run in the game; the full race has not been played through.
`spacerace.ini` ships with `test_mode = 0` (1 = space research at 5 % cost, no year limits, for
testing). The seven Workshop items are uploaded and **public** on Steam (ids in section 11 and
in `tools/space_workshop.py` `ITEMS`).

## 2. Ground rules

- **Branches:** commit only to `unstable`. `dev` takes pull requests from `unstable` (two
  approvals); `main` takes pull requests from `dev` (code-owner approval, @aislanfoina). The owner
  may merge with admin bypass. Never push to `dev`/`main` directly.
- **Origin of this repo:** it is exported from a private mixed workspace (`wrsr`, which also holds
  the post-apocalypse mod) by `tools/export_spacerace.py`; the export replaces everything except
  `.git`. If you work in this repo directly, say so in the commit, so the workspace can be synced.
- **Commits** are authored as the owner; add a `Co-Authored-By:` line for the AI.
- **Never** enter Steam or other credentials, never change the owner's RML configuration (which
  plugins/items are enabled) without asking, never publish to the Workshop without an explicit go.
- Keep file formats byte-exact: `.gitattributes` is `* -text` (CRLF ini/scripts and binary models
  must not be rewritten). Write `.ini`/`.txt` the game reads with CRLF.

## 4. Build, install, run

- **Build:** `.\build.ps1` compiles every `mod/plugins/*` with MSVC (finds the toolset and SDK
  itself, sets INCLUDE/LIB directly - do NOT use `vcvars64.bat`, it breaks when
  `%ProgramFiles(x86)%` is missing, i.e. any shell started from Git Bash). `-Install` deploys the
  package, kit and rockets into `<game>\media_soviet\workshop_wip\<item id>`; `-Game` or
  `WRSR_GAME` sets the game folder. Close the game and RML first (RML holds `previewimage.png`
  open; the script refuses while they run).
- **Plugins ship in packages:** a plugin with `package.txt` naming `space_race` is copied into
  item 3814051864's `plugins/` with its ini, `rml.json` and `data/` (as `<name>_data`). RML switches
  plugins with their item. Do not put DLLs in RML's own `rml\plugins` (RML files them all under
  its own item and toggles them together; Steam wipes that folder on RML updates).
- **RML development items default to off**: enable them (and the plugins) in RML's UI. The log line
  `Development inventory: local=N enabled=M` says whether they load.
- **Launching for a test:** start RML via Explorer, not from a sandboxed shell, or the game shows
  "STEAM ERROR: Can't initialize STEAM":
  `Start-Process explorer.exe -ArgumentList '"<RML>\RepublicModLoader.exe"'`, then
  `python tools/dev/rml_launch.py` (posts the click on "Launch"). Never type Steam credentials; a
  "Refresh Sign In" prompt is the owner's to answer.
- **Logs:** RML `<workshop>\784150\3787969749\rml\logs\rml-runtime.log` (plugin lines tagged
  `[Tesmio:space-race.<plugin>]`; `WRSR process exit: ... code=0x...`); the game's
  `SovietRepublic\log.html` (strip tags; base-game noise: `ResourceGet - not found waste`,
  `Read error (8)` on `replace_history.bin` / `usedveh.bin`).
- **Regenerating content:** see README "Rebuilding the content". Order: `build_space.py`
  (textures, kit, rockets, previews, Workshop posters via `space_thumbs.py`; needs Blender 5.2) -> `space_research.py` ->
  `space_scenario.py` (checks the rendered programme with `tools/vmcheck.py`) -> `space_settings.py`
  -> `space_workshop.py`. `build_space.py inis` rewrites only the kit's building files (both goods
  variants). `space_layout.py` checks truck bays against the models.

## 5. Architecture

### spacerace plugin (`mod/plugins/spacerace/spacerace.cpp`)
Hooks (installed in `TsmPluginStart`):

| Hook | Target | Why |
|---|---|---|
| IAT `api-ms-win-crt-stdio-l1-1-0.dll!fopen` | SOVIET64 import | serves a merged `research/research.ini` (vanilla + our branch) and patched kit `building.ini` files |
| IAT `C3DDLL64.dll!?GetString@C3D_LANGUAGE@@QEAAPEA_WH@Z` | | answers our string ids 591000-591999 from `strings.txt` |
| inline ScenarioEnumeration `0x5CB7C0` (18-byte prologue) | | auto-starts the programme in an ordinary game; then applies the running mission's launch rules |
| inline TickAllBuildings `0x139A70` (post) | | pad linking, launches, rocket bills (other plugins hook it too: chain on the live bytes) |
| inline ResourceField `0x59B3F0` | only with new goods | maps `vm_goods` names to the spare Resources fields so scripts can read added goods |
| inline CanUseBuilding `0x3E2900` | | pad rule: each rocket only on its pad kind; chained after another plugin's 14-byte `FF 25 00000000 <addr>` jump |

Jobs:
1. **Install data** into `media_soviet` (research icons, scenario folders, goods icons).
2. **Research branch:** merged research.ini written beside the DLL; `$UNLOCK_RESEARCH` lines
   injected into vanilla parents (`inject.ini`: advanced_engineering, electronics_1); `{KIT}`
   replaced by `kit_item`; `[research]` settings rewrite `$YEAR`/`$COST`; `test_mode` drops years
   and scales costs.
3. **Names** for ids 591000+.
4. **Programme auto-start:** in the enumeration hook, an empty scenario string (an ordinary game)
   gets `spacerace / <mission>` + auto-start flag (std::strings at 0x9E8648 scenario, 0x9E8668
   mission, flag byte 0x9E8688; assign helper 0x8EB20(this, ptr, len)) - what a map's
   `$ScenarioAutoStart` does. Saves already running a scenario are left alone.
5. **Pads to the MIK:** unlinked `sr_pad_*` get the nearest `sr_mik` within `link_range` (pad+0x5B0
   = MIK, then 0x3BB8F0(game, MIK, pad)); the game's own placement linking did not work for them.
6. **Settings** (see section 7): building files patched at load, the programme rendered from a
   template into `race_<fnv hash>`, `rules.ini` per mission read on every world load.
7. **Launches:** the script flags the rocket with `Vehicle_SetCanSell(veh, 0)` (byte vehicle+0x38A,
   readable as `vehi.bDisableSell`); the plugin sees the flag, takes the rocket's load from STORAGE
   buildings within the radius (`TakeLoad`), lifts both world matrices for `climb_seconds` (height
   `1.2 s^2 + 0.25 s^3`), spawns flame/smoke/pad steam particles, then clears the flag; the script
   sells the rocket. A rocket removed mid-climb (failure) gets an explosion and 8 s of smoke.
8. **Rocket bills:** each rocket type's bill of parts (type+0x85C8, 16-byte {Resource*, float}
   entries, computed by 0x3F8D10 from empty weight) is rewritten to `[rocket_parts]` (new goods
   only); the workers entry stays; shadow copies (`ident` starting "shadow") are skipped.

### experts plugin
A fourth education tier: education is one uncapped float at person+0xA8 (`[0,1)` none, `[1,2)`
basic, `[2,3)` higher); the game only tests >=1/>=2, so `[3,4)` is a save-safe "expert" tier.
Jobs are handed out day by day, so per-person time never accumulates: the plugin keeps an
in-memory **class per training building** (`class_size` seats, best-educated eligible staff first,
one class per citizen) and raises the whole class daily, scaled by eligible staff / class size.
`experts.ini`: Star City `sr_training` (365 days per tier, 40 seats, age 23-35, health >= 0.8, up
to 3.0), OKB-1 `sr_bureau` (730 days, 20 seats, age 30-65, up to 3.6). Test installs often set
`days_per_tier = 30` in the deployed copy.

### resources plugin (port of TesmioLoader's)
Adds six goods by claiming spare records in the engine's resource vector (RVA 0x9E11C0, 832-byte
records, 57 live, room for 63; ResourceGet hooked at 0x2AA830): `rocket_stage` (template aluminium),
`rocket_engine` (mcomponents), `avionics` (eletronics), `lox` (oil), `hypergolic` (oil),
`spacecraft` (eletronics). `tools/port_resources.py` regenerates it from the vendored source (ini
beside the DLL, hooks in TsmPluginStart, safe defaults). It reads `spacerace.ini`: with
`new_goods = 0` it adds nothing and only hooks ResourceGet to **alias** the six names to their
stand-ins (see section 8).

### The programme (scenario VM)
`data/programme/race.tmpl` is generated by `tools/space_scenario.py` (114 `@tokens@`: American
dates, loads, failure odds, crew, tracking, rewards, goods fields, staff numbers of tracking
stations/test stands). The plugin renders it with the settings into
`media_soviet/scenarios/spacerace/race_<hash>/` (+ `rules.ini`: radius, loads) and starts that
mission in new games. Rockets are recognised by engine power 9001-9005 (the VM's Vehicle struct has
no type name); tracking stations and test stands by their staff numbers. Failure chance =
milestone base - 5 % per earlier success of that rocket - 10 % with an engine test stand (- 35 %
NK-33 for the N1), floor 5 %; a failure starts a fire (if fires are on) or closes the pad for
`pad_repair_days`.

## 6. Engine facts used (1.1.1.9)

```
game context            static object at RVA 0x9D4F10 (passed to TickAllBuildings)
  +0x11B08 buildings vector   +0x126A8 persons   +0x12810 vehicles
  +0x11778 research vector (0xE8 records: name +0, progress float +0xD0, 1.0 = done)
  +0x590 day  +0x594 year
building  +0x318 type descriptor (ident "<item>/<object>" at +0, BUILDINGTYPE at +0x360)
          +0x320 C3D_NODE (position via C3DDLL64 C3D_NODE::GetPosition)
          +0x5B0 parent  +0x5B8 child vector (add with 0x3BB8F0(game, parent, child))
          +0x970 std::vector<Storage> (stride 0xE0; storage+0/+8 slot vector of {Resource*, float content, float limit})
          types: STORAGE 5, PRODUCTION_LINE 0x28, AIRPLANE_PARKING 0x2F; airplane subtype 0x21 accepts vehicle types 8 and 10 (helicopter)
person    +0x40 building it is in now (never home)  +0x58 customs house it immigrated through
          +0x80 workplace  +0xA8 education  +0xD4 age  +0xE0 health
vehicle   +0x1708 type (ident at type+0x200)  +0x38A no-sell flag
          world matrices +0xD60 and +0x1080 (each followed by its inverse), position copies +0xDE0 / +0x1100
vehicle types   vector at RVA 0x9E7750, stride 0x9F08, bill of parts at +0x85C8
building types  table at RVA 0x9E6A30, stride 0xBE8; construction phases at +0x370/+0x378
                (0x21B8-byte records, each a vector of {Resource*, float, pad})
resources       vector at RVA 0x9E11C0, stride 832, name at +0
particles       library at [RVA 0x9941F0]+0xF60; C3DDLL64 GetEffect(lib, char*), SpawnParticles(effect, pos*, dir*, 1, 1.0, 1.0, 0)
building ini    loaded through the fopen import (call 0x10E37E in the type loader 0x10E1F0)
research.ini    opened by the fopen import after C3DPath_GetFullPath (0x2F3D12)
0x3E2900        CanUseBuilding(ctx, building, vehicle type, flag, x)
0x59B3F0        ResourceField(vm, name): string-compare chain over vanilla names, unknown -> 0 (= the workers field!)
```

## 7. Settings (`mod/plugins/spacerace/spacerace.ini`)

`[general]`: `kit_item` (the kit's Steam item id, 3814049784; it was 9000101 during development),
`autostart`, `research`, `scenario`/`mission` (base name of rendered missions), `link_range`,
`test_mode`/`test_cost`, `new_goods`. Below the marker, written by `tools/space_settings.py` from
the generators (and mirrored in `data/defaults.ini`, read first): `[research]`, `[america]`,
`[milestones]`, `[rockets]`, `[rocket_parts]`, `[launches]`, `[rewards]`, `[buildings]`,
`[building:sr_*]` (cost: absolute amounts - defaults measured from the game with
`tools/dev/costdump.py kit`, kept in `tools/space_kit_costs.txt`; workers, educated, production,
consumption). Research, buildings and rocket parts apply to every game at start-up; programme rules
are fixed per game (a save keeps its `race_<hash>` mission).

## 8. Saves and compatibility

- **A save keeps its running script** (`runningScripts.bin`). Never change a mission under existing
  saves: rewrites get a new folder, old ones are frozen in `legacy/` (`programme`, `race`). Rendered
  `race_<hash>` folders in media_soviet must never be deleted.
- **Goods (tested 2026-09-30):** `stats.ini` lists per-resource data by name (`$end`-terminated
  sections). A plain save loads with `new_goods = 1` and the goods join. A new-goods save loads with
  `new_goods = 0` but the **save writer crashes (0xC0000005) on warehouse slots of the unknown
  goods** - hence the alias: with goods off, ResourceGet answers the six names with the stand-ins'
  records (lox/hypergolic -> chemicals, rocket stage/engine -> mcomponents, avionics/spacecraft ->
  eletronics), and the next save is clean. No converter tool needed.
- Research entries added to an existing save are fine. Not tested: loading a modded save with the
  plugins switched off entirely.

## 9. Testing

- **Offline first.** `tools/vmcheck.py` checks VM scripts (argument types, function endings,
  fields; clean on all 71 vanilla scripts). For plugin file logic (settings, research rewrite,
  building patches, programme rendering) compile `spacerace.cpp` into a console exe with a stub
  `TsmHost` (`log`, `readablePtr`, `faultFilter`) and run its functions on a copy of the data; the
  rendered programme for unchanged settings must be byte-identical to
  `build/space_programme_default_goods0/1.txt`.
- **In game** (Windows, 5120x1440 primary monitor; coordinates are physical pixels):
  `tools/dev/gdrive.py shot|crop|click|move|key|type` (focus stealing works; camera keys need
  scan codes). Main menu: Custom Game (1960,723), Load Game (1960,777), confirm (3117,1300);
  custom map "Flatland with hills" (2700,843), Start (3117,1330). In game: settings icon (40,167)
  -> save-as (207,293) -> "Create new save" (3000,965) -> confirm (2700,733) (typed names do not
  reach the field); load (287,293) -> row -> (2950,960) -> confirm (2700,733). ESC opens nothing.
  Red rows in the load list are autosaves. Autosaves overwrite slots within minutes: copy a sample
  out first if you need it.
- **Memory probes:** `tools/dev/memprobe.py`, `memscan.py` (read-only), `costdump.py`,
  `storage_fill.py` / `research_unlock.py` (write - test saves only).

## 10. Traps that already cost time

1. The game shows **every model mirrored** left-right versus Blender. Lettering is built mirrored
   (`srkit.mtext`); README renders are flipped to match the game.
2. `building.ini` has **no comment syntax**: any token starting with `$` is a directive anywhere.
3. `$CONNECTION_ROAD` / `$CONNECTION_PEDESTRIAN`: outside point first, lot edge second.
4. Lots: full-footprint plates are podiums (`LIFT` 0.40, skirt 2.6 m) or terrain shows through.
5. The **VM** has no `>=`, `<=`, `==`, `!=`; `?` is equality; every non-main function must end with
   `return(x)`/`returnVoid()`; no negative literals (write `0.0 - x`); the Resources calls only
   **read** building stock (a plugin must take goods).
6. Added goods are invisible to scripts (ResourceField returns the workers field) unless mapped.
7. The MIK (aircraft production line) needs a **linked pad** before it offers rockets, a bought
   blueprint, and `$CONSUMPTION` lines for **every** good of the bill or parts show "missing".
8. A shared inline hook must not reach past the first owner's stolen bytes; chain on the exact
   14-byte absolute jump another plugin left (see CanUseBuilding).
9. `TsmHost::log` is not printf: width specifiers (`%-24s`) break argument consumption. Format into
   a buffer, log `%s`.
10. Plugin inis: read them from the DLL's own folder (module path); RML's config API resolves
    elsewhere.
11. PowerShell 5.1 mangles inner double quotes in native arguments (e.g. `gh --jq`); write output
    to a file and parse it. The Bash tool mangles backslashes in heredocs - write scripts to files.
12. Launching RML from a sandboxed shell -> "STEAM ERROR" (start it via Explorer).
13. N1 pad: auto costs made it enormous; its cost factor was cut to 0.25 and is now an absolute
    setting (203,149 workdays default).

How an upload works: Workshop -> Your items (WIP) -> the item's Edit item page -> the green check
("Save changes"). For an item Steam knows, that check IS the upload ("Connecting to STEAMWORKS",
"Uploading item..", "Item uploaded successfully"); there is no separate upload button, and items
with local placeholder ids (90001xx) only save locally. **Every upload also sets the visibility**
from the page (`$VISIBILITY` in workshopconfig.ini, the game's values: 0 unpublished, 1 friends
only, 2 public - not Steam's enum, where 0 is public). The items are public now, so
`space_workshop.py` writes 2; uploading with 0 would hide the mod. Check the page says Public
before pressing the check. Steam's public API shows the live state (GetPublishedFileDetails,
`visibility` in Steam's enum).

**Without the game: `tools/workshop_upload.py`** updates title, description, preview, content,
visibility and Required Items (or creates items) through the signed-in Steam client, using the
game's own `steam_api64.dll` (flat API, ISteamUGC v012) as app 784150 - no password. Ids, texts,
visibility and Required Items come from the packer's `workshop_items()`; preview and content come
from the installed `workshop_wip/<id>` folder (run `build.ps1 -Install` first; content uploads refuse
while the game or RML runs, or when plugin-generated files are in the folder). `--check` reports
sign-in and differences from the live store pages without sending anything. **It must run outside
any sandbox**: from an AI agent's sandboxed shell `SteamAPI_Init` fails (the game fails the same
way), and the agent's auto mode treats uploads as publishing - both are the owner's permission
settings to grant. Interfaces come from `SteamInternal_FindOrCreateUserInterface` (the SDK's own
accessor route): the legacy `SteamClient()` + `SteamAPI_ISteamClient_GetISteam*` route returned a
null interface with this DLL. Status 2026-10-05, verified against Steam by the owner: `--check`,
`description` (kit, main item), `collection` (CreateItem, title/description/preview/visibility,
AddDependency - so the `create` and `required` code paths are proven too); `content` not yet.

**Uploading the plugins item (3814051864):** the plugins write files into their own item folder
at start-up (`spacerace_data/buildings/*.ini`, `research_merged.ini`, `tesmioloader.resources.log`)
and RML has its DLLs loaded, so uploading it from a game started through RML fails with "Unknown
Error (Error code 2)" (Steam's generic failure). Close the game and RML, re-run
`build.ps1 -Install` (replaces the folder, dropping the generated files), start the game straight
from Steam (no RML, so no plugin loads) and upload from there. Kit and rockets upload fine either way.
